### 3.2 Install and upgrade

- Docs (https://vercel.com/docs/cli) show `npm i vercel` / `bun i vercel`. The changelogs and the update banner say `npm i -g vercel@latest`. **Use a single global install.** The user's CLI is npm-global (`/opt/homebrew/lib/node_modules/vercel`), so:
  ```bash
  vercel upgrade --dry-run   # shows the command it will run
  vercel upgrade             # -> npm i -g vercel@<exact latest> (60.1.3)
  vercel --version
  ```
- Do not also `bun add -g vercel`. Two global installs shadow each other on PATH. Do not add `vercel` as a devDependency either: it is a large package and gets installed on every Vercel build.
- Native binary (`@vercel/vc-native`) is still "experimental". Skip it.

### 3.3 Recommended flow (Bun, Next.js, Git-connected project)

```bash
# once per machine
vercel login                     # OAuth device flow
vercel whoami                    # 60.x also prints the plan

# once per checkout / worktree (.vercel/ and .env.local are gitignored and per-directory)
vercel link --yes --project max.vonstorch.com      # only one team, so the scope auto-resolves
vercel env pull                  # Development vars -> .env.local (Next.js loads it automatically)
```

- `vercel pull` (settings + `.vercel/.env.*.local`) is only needed for `vercel build` / `vercel dev`, so it is **not needed** here.
- Superset worktrees: each worktree needs its own `vercel link` + `vercel env pull`. You can also export `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` so linking is promptless.

Preview and production deploys:

## 4. Project configuration: none vs vercel.json vs vercel.ts vs vercel.toml

Facts (https://vercel.com/docs/project-configuration, /vercel-ts, /vercel-toml, changelog 2025-12-19):
- Three equivalent file formats support the same properties: `vercel.json` (static), `vercel.toml` (static, allows comments, new in 2026), and `vercel.ts` (`.js/.mjs/.cjs/.mts`, runs at build time, needs `@vercel/config`). **You can use only one file per project.**
- The docs are **neutral**. The Vercel plugin skills (v0.50.0 `knowledge-update`, `vercel-functions`) say "vercel.ts is now the recommended way". **Conflict, flagged.**
- vercel.ts costs: a 0.x dependency (`@vercel/config` 0.7.2, which pulls in `zod@3`), plus a pre-config-compilation install step during `vercel build` (described in GitHub issue #17577; CLI patch b7ec19b). That is more moving parts for no gain here.

Does this project need a config file? **No.**
- Framework, install and build are auto-detected. Node version is set in Project Settings (24.x); also pin it in `package.json` `engines`.
- Fluid is already on for the project. Region is a Project Setting (Hobby allows a single region).
- Headers, redirects and rewrites go in `next.config.ts` (framework-native).
- No crons are needed: Spotify freshness comes from ISR, not cron. No `bunVersion` (see §5.3).

If one appears later (for example to pin `regions` in code), use the smallest static file:
```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "regions": ["fra1"]
}
```
Use `vercel.ts` only if you need dynamic logic.

## 5. Runtime

### 5.1 Node.js 24 + Fluid compute
- Available versions: 24.x (default), 22.x, 20.x. **Node 20 is deprecated for builds and functions on 2026-10-01**, so check with `vercel project ls --update-required`. This project is already on 24.x. Only major versions can be pinned, and `engines.node` overrides the dashboard.
  ```json
  { "engines": { "node": "24.x" } }
  ```
  Use `24.x`, not `>=24`: a range maps to the "latest available", so it would silently jump to 26 when Vercel adds it.
- **Local Node is 25.8.1 (EOL 2026-06-01).** Use Node 24 LTS locally for parity. `next dev` runs on the local Node even when started via `bun dev`.
- Fluid compute has been the default for new projects since 2025-04-23 and is **on** here. It includes bytecode caching for Node (production only), Active CPU pricing and in-function concurrency. Hobby: 300 s max duration, 4 CPU-hrs Active CPU, 360 GB-hrs memory, 1M invocations.
- Function region is **iad1**. Hobby allows one region. **Match it to the Upstash primary region** (for example `fra1` if the DB is in eu-central-1). The ISR cache also lives in the function region. Check this with the backend agent (the Upstash region was not inspected).

### 5.2 Bun install detection (bun.lock)
- `bun.lock` gives `bun install` (Bun >= 1.2). `bun.lockb` gives Bun < 1.2. Detection is automatic (https://vercel.com/docs/package-managers). `packageManager` / `devEngines` pins only affect pnpm/corepack, not Bun (verified in `@vercel/build-utils` source).
- **Gotcha (important): Bun 1.4 writes `bun.lock` with `lockfileVersion: 2`** (https://bun.com/blog/bun-v1.4, "Upgrading to 1.4"). Before the fix, Vercel's build container installed with bundled **Bun 1.3.14**. It printed `UnknownLockfileVersion … warn: Ignoring lockfile` and **silently re-resolved every dependency**, so the build still passed. `bunVersion` did not help (GitHub issue vercel/vercel#17577).
- Fix: build-utils routes lockfileVersion >= 2 to `/bun1.4`. I verified this in the published source of `@vercel/build-utils` 14.10.1 (the first version, shipped with **vercel@59.17.0**) and 14.13.1 (vercel@60.1.3): `lockfileRequiresBun14(lockfileVersion) ? {path:"/bun1.4"…}`. Vercel staff said on 2026-09-15 that it was "released on the build container". A user saw the container still on CLI 59.16.0 on 2026-09-18. **Current container rollout is UNVERIFIED.**
- Action after upgrading local Bun to 1.4.2 and re-running `bun install`: in the first build log, confirm the `Vercel CLI` line is >= 59.17.0 and that it says `bun install v1.4.x` with no "Ignoring lockfile". Fallback if not: set the Install Command to `npx -y bun@1.4.2 install --frozen-lockfile`, or keep local Bun on 1.3.x until it works.
- Other Bun 1.4 breaking changes that touch this repo: when invoked as `node` (`bun --bun …`) Bun no longer loads `.env*` files. That does not matter for `next dev`, because Next loads env itself. `bunfig.toml` parsing is strict, but the repo has no bunfig.

### 5.3 Bun runtime for Vercel Functions: evaluation
- Status: **Public Beta** since 2025-10-28. Bun 1.4 has been available since 2026-08-20 as an explicit opt-in. Enable it with `"bunVersion": "1.4.x"` (or `"1.x"`, which is 1.3.14) in vercel.json / vercel.ts / vercel.toml. Only those two values are valid. It applies to all non-Edge functions and Routing Middleware. Supported frameworks are Next.js, Express, Hono, Nitro and Elysia. It supports large functions (5 GB) and max duration up to 30 min (both beta, since 2026-08-24).
- Next.js + ISR on the Bun runtime requires `"dev": "bun run --bun next dev"` and `"build": "bun run --bun next build"`.
- Downsides:
  - Beta.
  - No automatic source maps, no bytecode caching, and no `node:http` request metrics.
  - A community report (2026-08-04) says Next 16.3 plus the Bun runtime fails at "Collecting page data" (`Expected CommonJS module to have a function wrapper`). The advice there was to drop the Bun runtime config.
  - Another report (2026-09-10) says `"framework": "bun"` was needed and octokit `#imports` failed.
- Vercel's own guidance: "Consider using Node.js instead if Node.js is already installed on your project and is working for you" (https://vercel.com/docs/functions/runtimes/bun). The benefit (28 % lower latency for CPU-bound SSR) is irrelevant for a site that is mostly prerendered and ISR.
- **Recommendation: do not enable.** Use Bun as package manager and script runner. The Node 24 runtime stays.
- **Guide conflict:** Bun's guides (https://bun.com/guides/deployment/vercel, https://bun.com/docs/guides/ecosystem/nextjs) say to set `bunVersion: "1.4.x"` and use `bun --bun next dev/build/start`. The Vercel docs say Beta and "prefer Node if it works". Next.js docs do not require Bun. **I follow Vercel and Next.js.**

## 7. Caching the Spotify result for hours (Next.js 16.3 on Vercel)

Options compared (current docs):

| Option | Status in Next 16 | On Vercel | Verdict |
|---|---|---|---|
| `export const revalidate = N` (route segment) | **Removed when `cacheComponents: true`** (route-segment-config version history, v16.0.0) | Classic ISR | Previous model only |
| `fetch(url, { next: { revalidate, tags } })` / `cache: 'force-cache'` | Previous model. It "keeps working as a separate layer", but the migration guide says to move it into `use cache` | Vercel "Data cache", persists across deploys | Awkward for Spotify (a token POST plus a GET; POST is not cached) |
| `unstable_cache` | Replaced by `use cache` | | No |
| **`'use cache'` + `cacheLife` + `cacheTag`** | **Current model (Cache Components)** | Output goes into the static shell. The prerendered HTML is kept in Vercel's durable ISR cache and revalidated in the background per `cacheLife.revalidate`. A failed revalidation keeps serving stale content and retries in 30 s | **Pick** |
| `'use cache: remote'` | For runtime-only caches (behind dynamic data) | Uses Vercel Runtime Cache (regional, billed; **shared across all projects on Hobby**) | Not needed: the Music page is static |

Recommended shape (patterns verified in https://nextjs.org/docs/app/getting-started/caching, /api-reference/functions/cacheLife, /getting-started/revalidating, /guides/migrating-to-cache-components):

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  cacheLife: {
    // optional custom profile; the built-in 'hours' = stale 5m, revalidate 1h, expire 1d
    spotify: { stale: 300, revalidate: 6 * 60 * 60, expire: 24 * 60 * 60 },
  },
}

export default nextConfig
```

```ts
// lib/spotify.ts
import 'server-only'
import { cacheLife, cacheTag } from 'next/cache'

export async function getTopTracks() {
  'use cache'
  cacheTag('spotify')
  try {
    const token = await getAccessToken() // refresh_token grant, a fresh token each time the function runs
    const res = await fetch(
      'https://api.spotify.com/v1/me/top/tracks?time_range=short_term&limit=10',
      { headers: { Authorization: `Bearer ${token}` } },
    )
    if (!res.ok) throw new Error(`Spotify ${res.status}`)
    const { items } = await res.json()
    cacheLife('spotify') // or 'hours'
    return items.map(/* only the fields the UI needs, serializable */)
  } catch {
    cacheLife('minutes') // do not pin a failure for hours; still prerenderable
    return null
  }
}
```

- The page just awaits `getTopTracks()`. There is no `revalidate` export. The route prerenders at build and is refreshed at most once per `revalidate` window, on traffic.
- Conditional `cacheLife` in branches is documented ("Conditional cache lifetimes"). Only one call may run per invocation.
- Trade-off of the catch: it prevents a failed **build** when Spotify is down, but during a runtime revalidation it replaces good data with the fallback for about 1 minute. Throwing instead keeps the stale page (Vercel ISR "On failure") but fails builds. The choice is the user's.
- `use cache` entries are keyed by build id, so **each deploy calls Spotify once at build**. Spotify credentials must be in the build env (Production + Preview). They are set for all three targets.
- Optional manual refresh from `/admin` (Server Action): `updateTag('spotify')` (immediate) or `revalidateTag('spotify', 'max')`. In Next 16 the second argument is required or recommended.
- **Guide conflicts:**
  - Vercel's ISR page still says "Next.js (App Router): Export `revalidate` from a route segment".
  - Vercel's Next.js page shows `fetch(..., { next: { revalidate: 10 } })`.
  - Both are the previous model. The Vercel PPR section and the Runtime Cache page do use Cache Components.
  - **I follow the Next.js 16 docs.**

## 9. BotID and Firewall rate limiting: plan note (details are with another agent)

The account is **Hobby**.

- **BotID Basic**: free on all plans. **Deep Analysis** (Kasada ML): **Pro only**, $1 per 1,000 `checkBotId()` calls; Enterprise is custom (https://vercel.com/docs/botid).
- **WAF rate limiting**: Hobby gets **1 rate-limit rule per project**, fixed window (10 s–10 min), keys IP or JA4, and 1,000,000 allowed requests included. Hobby gets up to **3 custom rules** total. Pro gets 40 rules, usage-based. Token bucket and header keys are Enterprise (https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).
- The `@vercel/firewall` `checkRateLimit('<id>')` SDK needs a dashboard rule with the `@vercel/firewall` condition. On Hobby it uses up that one rule.
- A **Server Action Name** condition (Next 15.5+) is available on all plans at no extra cost. That means 1 rule can rate-limit the Community Server Action by IP.
- Traffic denied, challenged or rate-limited by the WAF is **not billed** (since 2026-05-18).

## 11. Deprecations and changes vs 2024–2025 knowledge

- CLI release notes are no longer on GitHub (last was 58.4.4). Use https://vercel.com/docs/cli/release-notes. CLI source is now synced from an internal repo.
- `vercel login` with email, `--github`, `--gitlab`, `--bitbucket` or `--oob`: removed 2026-02-26. `team` (SAML): removed 2026-06-01. Device flow only.
- `now.json` support: removed 2026-03-31. Edge Config renamed **Global Config** (2026-07-29). The `vercel edge-config` alias remains.
- Node 18 is gone (2025-09-01). **Node 20 is deprecated for builds and functions on 2026-10-01.** Node 24 is the default (GA 2025-11-25).
- Fluid compute is the default for new projects (2025-04-23), with Active CPU pricing (2025-06-25). Edge Middleware and Functions run on Vercel Functions infrastructure. Standalone Edge Functions are discouraged.
- Env vars: the "Sensitive" toggle became **Config / Secret** (2026-08-24). The "Enforce Sensitive Environment Variables" policy is deprecated. `vercel env add --visibility`.
- `vercel env pull` keeps local-only vars (56.0.0). `vercel link` preserves `.env.local` (2026-06-23). `vercel env run` exists.
- Project linking resolves the team first (CLI 55, 2026-07-15).
- vercel.ts (2025-12-19) and vercel.toml (2026) exist alongside vercel.json.
- Bun runtime is in Public Beta (2025-10-28). Bun 1.4 is a Rust rewrite with lockfile v2 (2026-08-20).
- @vercel/analytics and speed-insights v2 (2026-03-10): MIT license, resilient intake, `endpoint` deprecated. **Speed Insights paid tier renamed "Speed Insights Plus"**, and a free tier now exists on all plans (2026-08-25).
- Next.js 16: `revalidate` / `dynamic` / `fetchCache` segment configs are removed under Cache Components. `experimental_ppr` is removed. `unstable_cache` is replaced by `use cache`. `revalidateTag(tag, profile)` and `updateTag`. `middleware.ts` is renamed `proxy.ts` (the Vercel Bun doc still says `middleware.ts`).
- Next.js 16.3: agent files are auto-generated. `vercel-labs/next-skills` is retired. next-devtools-mcp 0.4.0 is slimmed down. Immutable static assets are reused across deploys (2026-07-17).
- Hobby: 30-day default deployment retention (2026-04-27), and fewer retained deployments plus a 10 GB storage limit (2026-09-16). Vercel Authentication for **production** is free on all plans (2026-09-09). Skew Protection remains Pro/Enterprise only.
- Security: Next.js May 2026 release (13 advisories; fixed in 16.2.6+) and August 2026 release (16.3.3+). Vercel blocks deploys of CVE-2025-66478-vulnerable Next versions by default. The repo's `next@16.1.1` must be upgraded anyway.
