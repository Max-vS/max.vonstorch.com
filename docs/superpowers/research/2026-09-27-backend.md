# Backend research v2: Better Auth (owner-only), Spotify, bot protection, validation

Research date: 2026-09-26. Version 2 of this report, after the scope changes:
- Storage is now **Neon Postgres + Drizzle**. The data model, drizzle-kit workflow and non-auth rate limiting belong to research-data. Redis is reduced to §6.
- Auth is **Better Auth**. **Only the owner logs in** (`/admin`). Visitors never get accounts.
- Form libraries belong to another agent.

Method: npm registry, package tarballs (I read the 1.7.6 source), GitHub releases, official docs. **UNVERIFIED** marks what I could not confirm.

## 0. Decisions

| Topic | Pick | Reason (one line) |
|---|---|---|
| Auth product | **Self-hosted Better Auth 1.7.6** + Drizzle adapter, tables in the app's Neon DB | Latest version, full control, no extra service. |

| Public submit | Vercel BotID Basic (free) + rate limit from research-data + moderation | Unchanged. |

## 2. Better Auth for one owner

### 2.1 Changes since 2025 that matter here

- **1.4 (2025-11-21):** stateless mode without a DB (not needed). https://better-auth.com/blog/1-4
- **1.5 (2026-02-28):** dynamic base URL (`allowedHosts`) "for Vercel preview deployments"; CLI renamed to **`auth`** (`npx auth …`, replaces `@better-auth/cli`); adapters moved to packages (`@better-auth/drizzle-adapter`, …); database after-hooks now run after the transaction. https://better-auth.com/blog/1-5
- **1.6 (2026-04-06):** only one core breaking change: `session.freshAge` now counts from session `createdAt` (set `freshAge: 0` to disable). Also: origin check added to the password-reset request, non-blocking scrypt, experimental OpenTelemetry, `oidc-provider` plugin deprecated. https://github.com/better-auth/better-auth/releases/tag/v1.6.0 , https://better-auth.com/blog/1-6
- **1.7 (2026-08-17):** https://better-auth.com/blog/1-7 , release notes https://github.com/better-auth/better-auth/releases/tag/v1.7.0 , upgrade guide https://better-auth.com/docs/guides/1-7-upgrade-guide
  - `user.validateUserInfo` gate: can reject an identity before create-user or link-account (all methods).
  - `npx auth create-admin` (needs the admin plugin).
  - 1.7.0 keyed accounts on `(issuer, accountId)` with a new required `account.issuer` column — **reverted in 1.7.3 (2026-09-06)**: "We restored the 1.6 account core schema"; accounts are identified by `(providerId, accountId)` again. No `issuer` column in 1.7.6 (verified in `@better-auth/core` table definitions).
  - Joins moved to stable `advanced.database.joins`.
  - Dynamic base URL resolves the origin from `Host`; `x-forwarded-host` only with `advanced.trustedProxyHeaders: true`. "Vercel … unaffected."
  - OAuth `redirect_uri` derived per request host (multi-host).
  - Rate limits use the adapter's atomic operations.
  - Other 1.7 breaking changes concern OAuth-provider/MCP/SCIM/SSO/Electron/2FA-OTP/generic-OAuth plugins — none used here.
- **1.7.3 (2026-09-06):** schema validation at startup is **on by default, also in production**, and auth requests are **rejected** when the DB schema does not match (`advanced.database.validateSchema`, default `true`) → apply migrations before (or with) every deploy that changes auth config/version. https://github.com/better-auth/better-auth/releases/tag/v1.7.3
- 1.7.1–1.7.6: fixes only (CLI refuses to add required columns without defaults to populated tables; Drizzle relation/schema-validation fixes; hydration fixes).
- Telemetry is **off** by default (source: `BETTER_AUTH_TELEMETRY` or `telemetry.enabled` needed).

### 2.2 Official guides read (pairs) and conflicts

| Pair | Guide | Key content |
|---|---|---|
| Better Auth × Next.js 16 | https://www.better-auth.com/docs/integrations/next | `toNextJsHandler(auth)` in `app/api/auth/[...all]/route.ts`; `nextCookies()` plugin (must be **last**) for cookie-setting calls in Server Actions; `auth.api.getSession({ headers: await headers() })` in RSC/actions; Next 16 `proxy.ts`: optimistic `getSessionCookie(request)` or full `getSession` (Node runtime). |
| Better Auth × Drizzle | https://www.better-auth.com/docs/adapters/drizzle | `drizzleAdapter(db, { provider: "pg", schema })`; workflow `auth generate` → `drizzle-kit generate` → `drizzle-kit migrate`; joins need relations. |
| Better Auth × CLI | https://www.better-auth.com/docs/concepts/cli | `init`, `generate`, `migrate` (Kysely only), `create-admin`, `secret`, `check`, `upgrade`, `info`. |
| Better Auth × Vercel previews | https://better-auth.com/docs/guides/dynamic-base-url , https://www.better-auth.com/docs/reference/options | `baseURL: { allowedHosts, protocol?, fallback? }`; allowed hosts become trusted origins. |
| Better Auth × security | https://www.better-auth.com/docs/reference/security , https://www.better-auth.com/docs/concepts/rate-limit | Origin check + Fetch Metadata, cookie defaults, scrypt, rate limit storages. |
| Better Auth × Bun | none (`/docs/integrations/bun` returns 404) | CLI docs use `bun x auth@latest …`. |
| Better Auth × Neon (self-hosted) | none | Neon documents only its managed service. |
| Next.js × auth | https://nextjs.org/docs/app/guides/authentication , https://nextjs.org/docs/app/guides/data-security , https://nextjs.org/docs/app/guides/authentication-with-cache-components | Lists Better Auth; DAL pattern; re-check auth in every Server Action; session reads inside `<Suspense>`. |

**Conflicts (flag)**
1. **Drizzle import path:** installation page uses `better-auth/adapters/drizzle`; adapter page uses `@better-auth/drizzle-adapter`. Both work in 1.7.6 (`better-auth` depends on the package and still exports `./adapters/drizzle`). Use the package path.
2. **Proxy:** Better Auth shows a full DB-backed `getSession` in `proxy.ts`. Next.js says proxy should only do optimistic cookie checks and "should not be your only line of defense". Follow Next.js.
3. **Rate-limit default window:** docs say 60 s / 100; source 1.7.6 uses `window: 10`, `max: 100`. Source wins.
4. **Default Drizzle schema file:** docs say `schema.ts`; CLI source writes `./auth-schema.ts`. Always pass `--output`.
5. **Dynamic base URL header order:** the guide lists `x-forwarded-host` first; 1.7 release notes and source use `Host` unless `trustedProxyHeaders: true`. On Vercel both headers are equal → no impact.
6. **CLI name:** one 1.7.0 migration note still says `npx @better-auth/cli generate`; CLI docs and npm use `auth` 1.7.6.
7. **Token encryption:** "User & Accounts" page says tokens are not encrypted and suggests database hooks; the options reference and source have `account.encryptOAuthTokens: true`. Use the option.
8. **`init --database`:** docs say "currently SQLite only"; the CLI source also has a Postgres template (node-postgres `Pool` + `pg`).

### 2.3 Setup scripts: what each generates → sweet spot

| Command (`bun x auth@latest …`) | What it does | Verdict |
|---|---|---|
| `init` | Interactive scaffold: auth config (DB template; Postgres template = `drizzle(new Pool(...))` + `pg`/`@types/pg`), `auth-client.ts`, `app/api/auth/[...all]/route.ts`, writes `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL` to **`.env`**, installs deps, many plugin flags | **Too much / wrong defaults**: writes `.env` (we use `vercel env pull .env.local`), may add `pg` against the Neon driver research-data picks. |
| `generate` | Writes Better Auth tables as a Drizzle schema file (default `./auth-schema.ts`, `--output` to change). Works without a DB connection for Drizzle. Loads `.env` and `.env.local` itself. | **Use it.** Tracks upstream schema changes (e.g. the 1.7.0 account change and its 1.7.3 revert). |
| `migrate` | Applies schema directly — **Kysely adapter only** | Not for Drizzle. |
| `create-admin` | Creates the first user through the admin plugin's `createUser` | Needs the admin plugin → skip. |
| `secret` | Prints a secret | Handy for `BETTER_AUTH_SECRET`. |
| `check schema` | Verifies the Drizzle schema object can hold Better Auth data (not that migrations ran) | Good CI check. |
| `upgrade` | Bumps `better-auth` + `@better-auth/*` to the CLI version | Use before `generate` on upgrades. |
| Hand-written Drizzle auth schema | You maintain every column | Error-prone, and 1.7.3+ rejects auth requests on a schema mismatch. Skip. |

**Sweet spot:** write 4 small files by hand (§2.6, ~90 lines) + `auth generate --output` + drizzle-kit + a 12-line seed script. Do not run `init`.

CLI gotchas (from source):
- The CLI **cannot load an auth config that imports `server-only`** ("Please remove import 'server-only' from your auth config file temporarily"). Keep `server-only` in the DAL, not in `lib/auth.ts`.
- It resolves tsconfig path aliases and handles the first run where `lib/auth.ts` imports the not-yet-generated schema file.

### 2.4 Owner-only sign-in: options → pick

| Option | Moving parts | Security | Verdict |
|---|---|---|---|
| **Email + password, `disableSignUp: true`, seed script** | 0 external apps; 1 seed run per database | scrypt hash; built-in rate limit; strong unique password; optional TOTP later | **Pick** |
| GitHub OAuth + `validateUserInfo` allowlist (owner's GitHub id/email) | GitHub OAuth App(s) + secrets; callback per host; previews need the `oAuthProxy` plugin | Inherits GitHub 2FA/passkeys | Good if you want no password; more setup |
| Admin plugin + `auth create-admin` | +plugin, +5 columns, +~13 endpoints | Endpoints gated by role, but more surface | Skip (only buys the seeding command) |
| Passkey (`@better-auth/passkey`) | +package, +table, first a password/other login to register | Phishing-resistant; domain-bound (not on previews) | Optional later |
| Magic link / email OTP | + email provider | Depends on mailbox | Skip (extra service) |

Seeding with sign-up disabled: `disableSignUp` blocks `/sign-up/email` **even for server calls** (source: `if (!enabled || disableSignUp) throw "EMAIL_PASSWORD_SIGN_UP_DISABLED"`). So the seed script builds a second instance with sign-up on for that one call (public APIs only, §2.6).

### 2.5 Neon Auth (managed Better Auth) vs self-hosted → self-hosted

| | Neon Auth | Self-hosted Better Auth |
|---|---|---|
| Status | GA; server on Better Auth **1.4.18**; SDK `@neondatabase/auth` **0.5.0-beta** (all versions beta) | 1.7.6 |
| Data | `neon_auth` schema in the same Neon DB/branch (Drizzle via `schemaFilter: ['public','neon_auth']` + `drizzle-kit pull`) | Your tables in `public`, generated by `auth generate`, migrated with drizzle-kit |
| Config | Console/SDK; roadmap: email/password, GitHub/Google/Vercel OAuth, admin plugin, webhooks, trusted domains; 2FA "coming soon"; **disable sign-up, rate-limit config, `validateUserInfo` not documented**; AWS regions only | Everything in code |
| Env | `NEON_AUTH_BASE_URL`, `NEON_AUTH_COOKIE_SECRET` | `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` |
| Cost | Free ≤60k MAU | Free |
| Branching | Auth follows DB branches | Also follows branches (tables are in the DB) |

Pick **self-hosted**: the owner-only lock-down needs `disableSignUp`, the allowlist gate and database rate limiting, which Neon Auth does not document; it also uses an older Better Auth and a beta SDK. Sources: https://neon.com/docs/auth/overview , https://neon.com/docs/auth/roadmap , https://neon.com/guides/neon-auth-nextjs

### 2.6 Code (Next.js 16, Bun, Drizzle, Neon)

```ts
// lib/auth.ts — no 'server-only' here: the Better Auth CLI must load this file
import { drizzleAdapter } from '@better-auth/drizzle-adapter'
import { betterAuth, type BetterAuthOptions } from 'better-auth'
import { nextCookies } from 'better-auth/next-js'
import { db } from '@/db' // Drizzle client from the data setup (research-data)
import * as schema from '@/db/schema' // re-exports the generated auth tables

const ownerEmail = process.env.OWNER_EMAIL?.toLowerCase()

// Each deployment trusts only its own URLs. Vercel sets these system env vars
// at build and runtime, without "https://".
const allowedHosts = [
  process.env.VERCEL_PROJECT_PRODUCTION_URL, // e.g. max.vonstorch.com (also set on previews)
  process.env.VERCEL_BRANCH_URL, // <project>-git-<branch>-<team>.vercel.app
  process.env.VERCEL_URL, // <project>-<hash>-<team>.vercel.app
  'localhost:3000',
  '127.0.0.1:3000', // Spotify rejects 'localhost' redirect URIs
].filter((host): host is string => Boolean(host))

export const authOptions = {
  database: drizzleAdapter(db, { provider: 'pg', schema }), // keep transaction: false (default) with neon-http
  baseURL: { allowedHosts }, // unknown hosts throw; allowed hosts become trusted origins

  emailAndPassword: { enabled: true, disableSignUp: true, minPasswordLength: 12 },
  socialProviders: {
    spotify: {
      clientId: process.env.SPOTIFY_CLIENT_ID as string,
      clientSecret: process.env.SPOTIFY_CLIENT_SECRET as string,
      scope: ['user-top-read'],
      disableSignUp: true,
    },
  },
  account: {
    encryptOAuthTokens: true,
    accountLinking: {
      trustedProviders: ['spotify'], // Better Auth's Spotify provider sets emailVerified: false
      allowDifferentEmails: true, // Spotify dev-mode /v1/me no longer returns email (Feb 2026)
      disableImplicitLinking: true, // link only through linkSocial() while signed in
    },
  },
  user: {
    validateUserInfo: ({ user, source }) => {
      // Spotify is only for the Music widget: link yes, sign in or sign up no.
      if (source.oauth?.providerId === 'spotify') {
        return source.action === 'link-account' ? undefined : { error: 'not_allowed' }
      }
      if (!ownerEmail || user.email?.toLowerCase() !== ownerEmail) return { error: 'not_allowed' }
    },
  },
  rateLimit: {
    storage: 'database', // memory (default) is per instance on Vercel
    customRules: { '/sign-in/email': { window: 15 * 60, max: 5 } },
  },
  plugins: [nextCookies()], // must stay last
} satisfies BetterAuthOptions

export const auth = betterAuth(authOptions)
```

import 'server-only'
import { headers } from 'next/headers'
import { cache } from 'react'
import { auth } from '@/lib/auth'

export const getAdminSession = cache(async () => {
  const session = await auth.api.getSession({ headers: await headers() })
  const owner = process.env.OWNER_EMAIL?.toLowerCase()
  return session && owner && session.user.email.toLowerCase() === owner ? session : null
})

export async function requireAdmin() {
  const session = await getAdminSession()
  if (!session) throw new Error('Unauthorized') // every Server Action calls this first
  return session
}

Optional `proxy.ts` (UX only, fast redirect; never the security check):
```ts
import { getSessionCookie } from 'better-auth/cookies'
import { NextResponse, type NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === '/admin/login') return
  if (!getSessionCookie(request)) return NextResponse.redirect(new URL('/admin/login', request.url))
}

export const config = { matcher: ['/admin/:path*'] }
```
`getSessionCookie` "only checks for the existence of a session cookie; it does not validate it" (Better Auth docs). It reads both `__Secure-better-auth.session_token` and `better-auth.session_token`.

### 2.7 Schema and migrations (fits the drizzle-kit flow)

```bash
bun x auth@latest generate --config lib/auth.ts --output db/schema/auth.ts --yes
bun x drizzle-kit generate   # SQL migration for app + auth tables together
bun x drizzle-kit migrate    # or research-data's migrate step
bun x auth@latest check schema --config lib/auth.ts   # optional CI check
```
- Tables for this config: `user`, `session`, `account` (identity = `providerId` + `accountId`; no `issuer` since 1.7.3), `verification` (OAuth state), `rateLimit` (only because `storage: "database"`).
- Re-run `generate` after changing Better Auth plugins/options and after upgrades (`bun x auth@latest upgrade`).
- Since 1.7.3 Better Auth validates the DB schema at startup (also in production) and **rejects auth requests on a mismatch** → run the migration before or with the deploy that needs it.
- Commit `db/schema/auth.ts`; re-export it from `db/schema/index.ts` so drizzle-kit and the adapter see it.
- Drizzle adapter default `transaction: false` → fine with the Neon HTTP driver; set `true` only with a driver that supports transactions (Pool).

### 2.8 Security notes

**Rate limiting (sign-in)** — verified in 1.7.6 source:
- Enabled when `NODE_ENV === "production"` (Vercel production **and previews**); off in `next dev`.
- Default storage `memory` (per instance → useless on Vercel). Set `storage: "database"`.
- Defaults: global 100 requests / 10 s per IP+path; `/sign-in*`, `/sign-up*`, `/change-password*`, `/change-email*` → 3 / 10 s; reset/verification mails → 3 / 60 s. Add a stricter rule (above: 5 per 15 min).
- IP from `x-forwarded-for` (default). Vercel overwrites this header "to prevent IP spoofing" (https://vercel.com/docs/headers/request-headers).
- **Gotcha:** the limiter and the origin check run in the HTTP router (`onRequest`). A Server Action that calls `auth.api.signInEmail()` directly **skips both**. Sign in with `authClient.signIn.email()`.
- Response `429` with `X-Retry-After`.

**Cookies** (source):
- `HttpOnly`, `SameSite=Lax`, `Path=/`. With a dynamic `baseURL` and no `protocol`, `Secure` + `__Secure-` prefix apply when `NODE_ENV=production`; local dev over http works without them.
- Keep `session.cookieCache` **off** (default): instant revocation, and there is a known issue where `getSession` in RSC returns `null` with cookie cache on (https://github.com/better-auth/better-auth/issues/7008).
- Session: 7 days, refreshed after 1 day (defaults). Optional: shorter `session.expiresIn` for admin.

**CSRF / origins**
- Better Auth checks `Origin` against trusted origins and uses Fetch Metadata for its HTTP routes; allowed hosts are added to trusted origins automatically (source). Extra origins: `trustedOrigins` or env `BETTER_AUTH_TRUSTED_ORIGINS` (comma list).
- Next.js Server Actions have their own Origin/Host check. Never set `disableCSRFCheck` / `disableOriginCheck`.

**Secrets and URLs on Vercel**
- `BETTER_AUTH_SECRET` (or `AUTH_SECRET`): ≥32 chars, high entropy (`bun x auth@latest secret` or `openssl rand -base64 32`). Set for Production, Preview and Development (separate values recommended). Rotation without logout: `BETTER_AUTH_SECRETS=2:new,1:old`.
- `BETTER_AUTH_URL`: Production `https://max.vonstorch.com`, Development `http://localhost:3000`, Preview **unset**. With the dynamic `baseURL`, requests use the matched host; `BETTER_AUTH_URL` is only the fallback for calls without a request (seed script). Better Auth does **not** read `VERCEL_URL` itself (source: it reads `BETTER_AUTH_URL`, `NEXT_PUBLIC_BETTER_AUTH_URL`, `PUBLIC_BETTER_AUTH_URL`, `NUXT_PUBLIC_*`, `BASE_URL`).
- **Preview hosts (picked):** build `allowedHosts` from Vercel system env vars (§2.6): `VERCEL_PROJECT_PRODUCTION_URL` (shortest production domain, "always set, even in preview deployments"), `VERCEL_BRANCH_URL` (`*-git-*.vercel.app`), `VERCEL_URL` (unique deployment URL). All are available at build and runtime, without `https://`. Each deployment then trusts only its own URLs — tighter than a wildcard. Requires the project setting "Enable access to System Environment Variables". https://vercel.com/docs/environment-variables/system-environment-variables
- Alternative: a wildcard like `'<project>-*-<team>.vercel.app'` (`*` = any chars except `/`). Better Auth's guide: avoid broad `*.vercel.app`. Vercel shortens generated URLs (63-char DNS label) and applies "anti-phishing" shortening for domain-like project names (docs example: `www-company-com` → `company`), so copy the real prefix. https://vercel.com/docs/deployments/generated-urls
- Unknown hosts throw (safer than setting a `fallback`).
- Previews are normally behind Vercel Deployment Protection already. The owner row must exist in the preview's DB branch (branch from production or run the seed there).
- With `encryptOAuthTokens`, a preview with a different secret cannot decrypt the Spotify token copied from production → Music is empty on previews (acceptable).

**Other**
- Page-level checks do not protect Server Actions: call `requireAdmin()` in each one (Next.js Data Security guide).
- Optional hardening: `twoFactor` plugin (TOTP; +1 table, +1 login step), `haveIBeenPwned` plugin, passkeys.

### 2.9 Other auth options (one line each)

- **Clerk** (`@clerk/nextjs` 7.9.7, native Marketplace): hosted user store outside your Postgres, a dashboard and a vendor account — overkill for one owner.
- **Neon Auth**: see §2.5 — older Better Auth, beta SDK, missing lock-down controls.
- **Better Auth admin plugin**: only buys `create-admin`; adds surface a single owner never uses.
- **Basic Auth in `proxy.ts` / jose password cookie / Sign in with Vercel / GitHub OAuth**: valid light options for one owner (v1 of this report), superseded by the Better Auth decision.

### 3.3 New storage: Better Auth linked account

How it works (verified in 1.7.6 source):
- Admin clicks "Connect Spotify" → `authClient.linkSocial({ provider: 'spotify', scopes: ['user-top-read'], callbackURL: '/admin' })`. Better Auth stores access/refresh tokens in `account` (encrypted with `encryptOAuthTokens`). Re-linking updates the same row and merges scopes.
- Server code (no request, no session) may call `auth.api.getAccessToken({ body: { accountId, userId } })`: "A trusted server-side `auth.api` caller with no session may instead name a `userId`". It refreshes when the token is within 5 s of expiry, stores the new tokens (incl. a rotated refresh token) and returns `{ accessToken, accessTokenExpiresAt, scopes }`. On a failed refresh it throws `FAILED_TO_GET_ACCESS_TOKEN`.
- Required settings (all in §2.6): `trustedProviders: ['spotify']` (provider sets `emailVerified: false`), `allowDifferentEmails: true` (no email in dev mode), `disableImplicitLinking: true`, provider `disableSignUp: true`, and the `validateUserInfo` branch that allows Spotify only for `link-account`.
- Spotify dashboard redirect URIs: `https://max.vonstorch.com/api/auth/callback/spotify` and `http://127.0.0.1:3000/api/auth/callback/spotify`. Linking locally: browse and sign in at `127.0.0.1:3000` (cookies are per host). Previews cannot link (host not registered).

```ts
// lib/spotify.ts
import 'server-only'
import { eq } from 'drizzle-orm'
import { cacheLife, cacheTag } from 'next/cache'
import { db } from '@/db'
import { account } from '@/db/schema'
import { auth } from '@/lib/auth'

async function getSpotifyAccessToken(): Promise<string | null> {
  const [row] = await db
    .select({ id: account.id, userId: account.userId })
    .from(account)
    .where(eq(account.providerId, 'spotify'))
    .limit(1)
  if (!row) return null
  try {
    const { accessToken } = await auth.api.getAccessToken({ body: { accountId: row.id, userId: row.userId } })
    return accessToken
  } catch {
    return null // refresh failed (e.g. 6-month expiry) → "Reconnect Spotify" in /admin
  }
}

export async function getTopTracks() {
  'use cache'
  cacheTag('spotify')
  const token = await getSpotifyAccessToken()
  if (!token) {
    cacheLife('minutes') // do not pin a failure for hours
    return []
  }
  const res = await fetch('https://api.spotify.com/v1/me/top/tracks?time_range=short_term&limit=3', {
    headers: { Authorization: `Bearer ${token}` },
  })
  if (!res.ok) {
    cacheLife('minutes') // includes 429 QUOTA_EXCEEDED
    return []
  }
  cacheLife('hours')
  const data = await res.json()
  return data.items.map(/* same mapping as today: name, artists, album.name, album.images[0].url, external_urls.spotify */)
}
```
- Generated Drizzle keys are camelCase (`providerId`, `userId`); check `db/schema/auth.ts` after `generate`.
- Admin page: call `getSpotifyAccessToken()` to show "Spotify connected / reconnect needed"; after linking, `updateTag('spotify')` from a Server Action (or `revalidateTag('spotify', 'max')` in a Route Handler).
- The refresh request uses Better Auth's default token-endpoint auth; a live refresh against Spotify is **UNVERIFIED** (not tested here).
- Fallback if you prefer no linking: one `spotify_auth` table (refresh token + authorized_at) + own OAuth start/callback (~60 lines, v1 design).
- `SPOTIFY_REFRESH_TOKEN` env var can be removed after the first link.

### 3.4 Caching (Next.js 16.3 docs)

- Presets: `minutes` (stale 5 min / revalidate 1 min / expire 1 h), `hours` (5 min / 1 h / 1 day), `days`, `max`. Custom profile in `next.config.ts` → `cacheLife: { spotify: { stale: 3600, revalidate: 43200, expire: 604800 } }`. https://nextjs.org/docs/app/api-reference/functions/cacheLife
- Conditional `cacheLife` per branch is supported (one call per invocation).
- `'use cache'` output joins the prerendered shell (durable on Vercel); entries reset on each deploy. https://nextjs.org/docs/app/api-reference/directives/use-cache

**2. Official guides**

- If GitHub login is preferred: allowlist the owner in `user.validateUserInfo` instead of `databaseHooks.user.create.before`. **5. Neon Auth vs self-hosted → self-hosted:**
- Neon Auth runs Better Auth 1.4.18, and its SDK has only beta versions (`0.5.0-beta`).
- Neon's docs show no disable-sign-up, rate-limit or `validateUserInfo` control.
- Neon Auth is AWS-only.
- Self-hosted Better Auth keeps its tables in the same Neon database, so auth still branches with the database (§2.5).

**6. Security**
- Sign-in rate limit on Vercel: **`storage: "database"`** (the `rateLimit` table). The memory default is per instance. The limiter is on only when `NODE_ENV=production` (production and previews). Source defaults: sign-in 3 per 10 s. Add 5 per 15 min.
- The limiter and origin check run only on HTTP requests to `/api/auth/*`. So sign in with `authClient.signIn.email`, not with `auth.api.signInEmail` in a Server Action.
- `BETTER_AUTH_SECRET`: at least 32 chars, one value per environment. `BETTER_AUTH_URL`: Production and Development only. It is the fallback for request-less calls such as the seed script.
- Trusted origins with changing preview URLs: Better Auth does not read `VERCEL_URL` or `VERCEL_BRANCH_URL` itself. Pass them, plus `VERCEL_PROJECT_PRODUCTION_URL` and localhost, into `baseURL.allowedHosts` (§2.6).
  - The allowed hosts become trusted origins automatically, and requests from any other host throw.
  - These variables exist at build and runtime, without `https://`, when the project setting "Enable access to System Environment Variables" is on. https://vercel.com/docs/environment-variables/system-environment-variables
- `requireAdmin()`: call it first in **every** admin Server Action. Page checks and `proxy.ts` do not protect actions (§2.6, Next.js Data Security guide).
- Deploy order: since 1.7.3, a missing migration makes auth fail at runtime. So migrate before or with the deploy.

**7. Spotify storage: confirmed, nothing depends on Redis.**
- The findings are storage-agnostic:
  - Spotify API changes and the 6-month refresh-token rule.
  - Refresh and rotation handling.
  - `invalid_grant` → reconnect.
  - `'use cache'` with `cacheLife('minutes')` on error and `'hours'` on success.
- Only v1's Redis key (`spotify:auth`) is replaced. There are two Postgres options:
  - **(a) Recommended with Better Auth:** the Better Auth `account` row. Link with `authClient.linkSocial`, read with `auth.api.getAccessToken({ body: { accountId, userId } })`. Better Auth handles refresh, rotation and encryption (`encryptOAuthTokens`). No extra table and no own OAuth routes (§3.3).
  - **(b)** A small key-value `settings` table, e.g. key `spotify`, value `{ refreshToken, authorizedAt }`. It needs about 60 lines of your own OAuth start/callback code and refresh code. Store the rotated `refresh_token` whenever Spotify returns one. It also works without Better Auth's Spotify provider.
